# Register, Login, and Logout - Technical PRD

## Overview/Problem

QuizMaker is a greenfield application for teachers who need to collaborate on a shared bank of multiple-choice questions. Before any of that collaboration can happen, each teacher must be a distinct user in the system. Today the starter app has no user model, no database, and no way to register or sign in. This feature adds the minimum identity layer: a persisted user record, hashed passwords, and HTTP endpoints plus pages so a teacher can register, log in, log out, and land on a stub MCQ page that later sprints will build out.

---

## Hypothesis

We believe that a simple register / login / logout flow with hashed passwords and a user table will let multiple teachers become identifiable users of QuizMaker, which is the prerequisite for later collaborative test-bank work.

---

## Scope

### In Scope

- Cloudflare D1 database bound as `DB`, plus a `users` table created by a Wrangler migration
- User fields: primary key, first name, last name, username, email, hashed password, timestamps
- Username and email stored as separate columns; they may hold the same value for a given user
- Passwords hashed with SHA-256 (Web Crypto) on the client before they are sent in an HTTP POST; the database stores only the hash; login compares hashes, never plaintext
- A user service in `src/lib/services/` with create, find, update, and delete
- HTTP POST endpoints for register, login, and logout; register and login call the user service
- Register and login pages; a logout control; redirect to an MCQ stub page after successful register or login
- An MCQ stub page with no question-authoring UI
- Test-driven implementation with **Vitest**: each phase starts with failing tests, then production code until those tests pass

### Out of Scope

- Multiple-choice question create / edit / delete / list (next sprint)
- Social logins (Google, Microsoft, etc.)
- Tokens (JWT, API keys, refresh tokens)
- Session management, cookies, CSRF tokens, and any "remember me" behavior
- Protected-route middleware (the MCQ stub is reachable without a server-side session)
- Email verification, password reset, account lockout, rate limiting
- Roles, permissions, or teacher/admin distinctions
- HTTP endpoints for user update or delete (the service methods exist for later use; they are not exposed)

### Cut

- **bcrypt / Argon2** — extra dependency and native/WASM friction on Cloudflare Workers; SHA-256 via the Web Crypto API needs no new package and runs in both the browser and Workers
- **Server Actions for auth** — project convention prefers Server Actions for mutations, but this feature explicitly requires HTTP POST endpoints, so App Router route handlers are the chosen surface
- **Route protection on `/mcqs`** — cannot be done honestly without sessions or tokens, which are out of scope
- **`@cloudflare/vitest-pool-workers`** — would run tests on the real Workers runtime and change how the whole suite runs; unit tests mock D1 and `getCloudflareContext()` instead. Raise it only if a later sprint needs true Workers integration tests.

## Technical Requirements

### Database Schema

Cloudflare D1 (SQLite). Create the database with Wrangler, bind it as `DB` in `wrangler.jsonc`, regenerate types with `npm run cf-typegen`, and apply the migration **locally only**.

Suggested database name: `quizmaker-2026` (matches `wrangler.jsonc` `name`). Binding name must be `DB`.

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY DEFAULT (lower(hex(randomblob(16)))),
  first_name TEXT NOT NULL,
  last_name TEXT NOT NULL,
  username TEXT NOT NULL COLLATE NOCASE,
  email TEXT NOT NULL COLLATE NOCASE,
  password_hash TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE UNIQUE INDEX idx_users_username ON users (username);
CREATE UNIQUE INDEX idx_users_email ON users (email);
```

| Column | Type | Rules |
|---|---|---|
| `id` | TEXT PK | Random 16-byte hex UUID generated by SQLite |
| `first_name` | TEXT NOT NULL | Trimmed; 1–100 characters |
| `last_name` | TEXT NOT NULL | Trimmed; 1–100 characters |
| `username` | TEXT NOT NULL | Unique, case-insensitive; 3–50 characters; letters, digits, underscores |
| `email` | TEXT NOT NULL | Unique, case-insensitive; valid email format; may equal `username` |
| `password_hash` | TEXT NOT NULL | 64-character lowercase hex SHA-256 digest; never plaintext |
| `created_at` | DATETIME | Set on insert |
| `updated_at` | DATETIME | Set on insert; bumped on update |

Normalize `username` and `email` to lowercase before insert and lookup so uniqueness is predictable.

### API Endpoints

All auth routes are App Router route handlers under `src/app/api/`. They are server-only. They must not import client components. Validate every body with a Zod schema before calling the user service.

Request bodies use `passwordHash`, not `password`. The client hashes first; the server never receives the teacher's plaintext password.

#### POST /api/auth/register

**Request Body:**
```json
{
  "firstName": "Ada",
  "lastName": "Lovelace",
  "username": "alovelace",
  "email": "ada@school.edu",
  "passwordHash": "64-char-sha256-hex"
}
```

`username` and `email` may be identical (for example both `"ada@school.edu"`).

**Response:**
- Success (201): `{ "id": "...", "firstName": "...", "lastName": "...", "username": "...", "email": "..." }` — never include `passwordHash`
- Error (400): validation failure (missing fields, bad email, bad username, `passwordHash` not a 64-char hex string)
- Error (409): username or email already taken
- Error (500): unexpected server error

#### POST /api/auth/login

**Request Body:**
```json
{
  "username": "alovelace",
  "passwordHash": "64-char-sha256-hex"
}
```

Login is by `username`. Because username may equal email, a teacher who registered with the same value in both fields can still sign in with that value.

**Response:**
- Success (200): `{ "id": "...", "firstName": "...", "lastName": "...", "username": "...", "email": "..." }` — never include `passwordHash`
- Error (400): validation failure
- Error (401): unknown username or hash mismatch (same message for both: `"Invalid username or password"`)
- Error (500): unexpected server error

Compare hashes with a constant-time check so mismatch time does not leak which field failed.

#### POST /api/auth/logout

**Request Body:** none (empty JSON object is acceptable)

There is no session, cookie, or token to invalidate. This endpoint exists so the client has a single, explicit logout call. It always succeeds.

**Response:**
- Success (200): `{ "ok": true }`

After the response, the client navigates to `/login`.

### User Interface Requirements

Use existing shadcn/ui pieces (`button`, `card`, `field`, `input`, `label`). Forms are client components because they must hash with Web Crypto before `fetch`. Do not add `react-hook-form`.

#### Home (/)

- Replace the starter landing content with a short QuizMaker intro and links to **Register** and **Log in**.

#### Register (/register)

- Fields: First name, Last name, Username, Email, Password, Confirm password
- Client validation before hashing:
  - All fields required
  - Password and confirm password match
  - Password at least 8 characters (checked on plaintext, then hashed)
  - Email looks like an email
  - Username 3–50 characters, `[A-Za-z0-9_]+`
- On submit: hash the plaintext password with SHA-256, POST `/api/auth/register` with `passwordHash`, never send plaintext
- Success: navigate to `/mcqs`
- Failure: show the server or validation message on the form; do not navigate

#### Login (/login)

- Fields: Username, Password
- On submit: hash the password, POST `/api/auth/login` with `passwordHash`
- Success: navigate to `/mcqs`
- Failure: show `"Invalid username or password"` (or the 400 validation message); do not navigate
- Link to `/register` for teachers who do not have an account

#### MCQ stub (/mcqs)

- Placeholder page titled for the future question bank (for example "Question Bank")
- Short copy that this area will hold MCQ authoring in a later sprint
- A **Log out** control that POST `/api/auth/logout` then navigates to `/login`
- No question forms, lists, or database calls

#### Logout behavior

- No cookie clearing and no token revocation (neither exists)
- Logout is: call the endpoint, then send the teacher to `/login`

## Testing Approach (Vitest, TDD)

This feature is built **test-first**. Vitest is the unit-testing framework (see `.cursor/skills/testing/SKILL.md`). Do not write production code for a phase until that phase’s tests exist and have been observed failing.

### Red → green → next phase

For **every** phase below:

1. Write the tests listed in that phase. Tests must assert observable behavior (return values, status codes, DOM the user can see, SQL that was prepared). Do not write assertions that cannot fail.
2. Run `npm test`. The new tests must be **red** (fail because the module, route, or UI does not exist yet, or because behavior is wrong).
3. Implement the minimum production code for that phase.
4. Run `npm test` again. The phase’s tests must be **green**. Existing tests from earlier phases must stay green.
5. Only then mark the phase **COMPLETED**. Acceptance criteria for the phase are not met while its tests are red or skipped.

If a test is skipped (`it.skip` / `xit`) to make the suite green, the phase is not done.

### Harness (install once, at the start of Phase 1)

Vitest is not in the starter. The user has asked for it, so add these **dev** dependencies (no other test runner):

```bash
npm install -D vitest @vitejs/plugin-react@4 @testing-library/react @testing-library/user-event jsdom vite-tsconfig-paths
```

Pin **`@vitejs/plugin-react@4`**. Unpinned `plugin-react@6` fails `npm install` here (`ERESOLVE` against `@babel/core@7` from shadcn).

- `vitest.config.ts` at the repo root with `@vitejs/plugin-react`, `vite-tsconfig-paths` (required for the `@/` alias), `environment: "jsdom"`, and `globals: true`
- Scripts: `"test": "vitest run"` and `"test:watch": "vitest"`
- Colocate tests: `src/lib/password.ts` is tested by `src/lib/password.test.ts`
- `vi.clearAllMocks()` in `beforeEach` where mocks are used
- Mock `getCloudflareContext()` and D1; never hit a real database or network in unit tests
- Stub `server-only` with `vi.mock("server-only", () => ({}))` if a module imports it
- Query Testing Library by role and accessible name; use `userEvent` rather than `fireEvent`

### What we do not unit-test

- `npx wrangler d1 create` and applying migrations against a live local D1 file (manual / checklist in Phase 1)
- Server Components that only compose client children (test the client form/stub components)
- Visual layout and the end-to-end browser pass (still required in Phase 4–5 alongside green tests)

### Implementation Patterns

Password hashing (client on submit; same helper is valid on the server if ever needed):

```typescript
export async function hashPassword(plaintext: string): Promise<string> {
  const bytes = new TextEncoder().encode(plaintext);
  const digest = await crypto.subtle.digest("SHA-256", bytes);
  return Array.from(new Uint8Array(digest))
    .map((b) => b.toString(16).padStart(2, "0"))
    .join("");
}
```

D1 queries stay in `src/lib/`, not in components:

```typescript
const { results } = await db
  .prepare("SELECT id, first_name, last_name, username, email FROM users WHERE username = ?1")
  .bind(username)
  .all();
const user = results[0];
```

Register/login client submit:

```typescript
const passwordHash = await hashPassword(password);
const response = await fetch("/api/auth/register", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ firstName, lastName, username, email, passwordHash }),
});
```

### Important Notes

- **No plaintext in transit or at rest (for this design).** The POST body carries `passwordHash`. The `users.password_hash` column stores that same value. This is not a substitute for TLS and is not a production-grade password scheme (SHA-256 is fast and unsalted). It is the agreed baseline for this sprint.
- **Client hashing does not create a session.** After 201/200 the UI navigates to `/mcqs`. Refreshing `/mcqs` does not "stay logged in" on the server because there is no cookie or token.
- **D1 is server-only.** Never import `src/lib/db.ts` or the user service into a `'use client'` module. The password helper is the exception because it has no binding access.
- **TDD is mandatory for Phases 1–4.** Write the phase’s tests, observe red on `npm test`, then implement until green. Do not implement a phase’s production code first and “add tests later.”
- **Approved test dependencies:** Vitest and the packages listed in Testing Approach. **Approved production dependency:** Zod for route-handler validation. Hashing uses the platform Web Crypto API. Ask before adding anything else.
- **Mock Cloudflare in unit tests.** `getCloudflareContext()` does not work under jsdom; supply a fake `env.DB`. Keep D1 behind `src/lib/` so tests mock that boundary.
- **Do not apply migrations with `--remote`.** Local apply only.
- **Do not deploy.**
- Unique indexes will throw on duplicate username/email; catch and return 409 rather than 500.

## Risks and Mitigation

### Technical Risks

- **Risk**: `npm run dev` (Node) does not behave like Workers; D1 via `getCloudflareContext()` may fail or look fine locally and break on Workers.
- **Mitigation**: Verify register/login against `npm run preview`, not only `npm run dev`.

- **Risk**: Duplicate username/email surfaces as a raw D1 error (500).
- **Mitigation**: Catch unique-constraint failures in the user service or route handler and return 409.

- **Risk**: Importing the user service into a client component bundles or breaks D1 access.
- **Mitigation**: Client pages only `fetch` HTTP routes and import `hashPassword`. Database code stays in `src/lib/` used by route handlers.

- **Risk**: SHA-256 without salt is brute-forceable if the database leaks.
- **Mitigation**: Accepted for this sprint. A later auth hardening sprint can add a slow hash and a server-side salt/pepper. Do not pretend this is production auth.

- **Risk**: Unit tests that call real D1 or Wrangler are slow, flaky, and fail in environments without Cloudflare credentials.
- **Mitigation**: Mock `getCloudflareContext()` and D1. Schema is asserted by reading migration SQL, not by applying it in Vitest.

- **Risk**: Implementing UI or routes first, then retrofitting tests, skips the red signal this PRD requires.
- **Mitigation**: Phase gate is “tests were observed failing, then passing.” Do not mark a phase complete if tests were written after the implementation.

### User Experience Risks

- **Risk**: Teachers expect to stay logged in after refresh; without sessions they will not.
- **Mitigation**: Copy on `/mcqs` can stay neutral; do not imply a durable session. Next sprint may add sessions if needed.

- **Risk**: Logout appears to "do nothing" because there is no session to destroy.
- **Mitigation**: Always redirect to `/login` after logout so the action has a visible result.

## Troubleshooting Guide

Populate this section when issues are found during implementation.

### D1 binding missing at runtime
**Problem**: `env.DB` is undefined or queries throw.
**Cause**: Binding not in `wrangler.jsonc`, types not regenerated, or running on Node without the Workers context.
